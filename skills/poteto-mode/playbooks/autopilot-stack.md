### Autopilot-stack

Build and verify a queue as one linear base-branch stack for the operator to land. Read pstack-runtime and Autopilot-full's lifecycle. A full-autonomy instruction does not change this playbook's operator-owned landing boundary.

1. **Build with durable ownership.** Follow Autopilot-full's owner loop through self-proof, CI, review triage, deslop, no-comments and babysit. Open draft PRs until proof is complete. Push authorized branch checkpoints after verifiable units, keep the decision trail and `children.tsv`, and report every code-ready patch SHA. Each writer owns an isolated checkout and branch.
2. **Audit hourly when supported.** Use Autopilot-full's scheduler binding, state-based liveness checks and stuck-child accounting. Register a real scheduler before promising later turns; otherwise checkpoint in-session and leave a handoff. Read the installed playbook and objective at each tick. Report only new tracked changes unless the user requested recurring status.
3. **Hold operator gates.** A request to state the plan does not authorize execution. On stop, hold all writers through available tools and persist the checkpoint.
4. **Verify each round.** Report code-ready when the code is final and STACK-READY when the owner's checks are green, each with exact head SHA. Follow Autopilot-full's verifier lanes, regression receipts and fix-forward loop with STACK-READY in place of merge-ready. Missing independent verification stays an unmet gate.
5. **Append only a verified patch.** A clean verdict permits adding the PR to the operator's linear stack in verified or specified order. Owners do not merge, arm auto-merge or close PRs. The root alone changes stack topology; owners build in parallel and report tip, current base and intended parent.
6. **Recheck topology changes.** Fetch the intended parent tip, rebase the candidate in its own clean checkout when necessary, publish only within authorization, and retarget through the supported PR tool/forge. Compare head/base and stable patch-id to the verdict. Shipping's build-equivalence rule may retain applicable production-build receipts for proved non-code changes; every other changed patch needs fresh verification. CI and mergeability run at the new head. Never treat a parent rebase or retarget as automatically safe.
7. **Deliver the operator's stack.** Confirm the ordered base-branch chain, current head/base SHAs, verdicts and remaining gates. Keep the objective and trail for resumption. Finish accounting for all active children. Landing starts only when the operator requests it through Shipping.

**Choosing between the autopilots.** Use Autopilot-full when the PRs are independent and landing authority is granted. Use Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** ordered PRs, current parents/head SHAs, verifier evidence, unresolved gates, ownership and state/trail paths. The operator receives a verified stack to review and land.
